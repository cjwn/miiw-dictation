# 米物接收器 Windows 协议笔记

这份笔记记录在 **Windows 10 19044 + VID `3044` / PID `507c` USB 接收器** 上实测得到的结论，
供以后维护、换固件、换机器时参考。里面每一条都对应一次踩坑，不是从文档抄来的。

## 1. 设备构成

接收器是一个 USB Composite Device，用 Windows 自带驱动（`usbaudio` / `hidusb`），
米物没有提供任何厂商驱动：

| 接口 | 类 | 用途 |
| --- | --- | --- |
| `MI_00` | Printer | 打印机支持接口 |
| `MI_01` | USB Audio | 麦克风（**必须由 `MI_05` 命令唤醒**才有 PCM） |
| `MI_03` | HID | 标准键盘 + Consumer Control |
| `MI_04` | HID | 鼠标 / 系统控制 |
| `MI_05` | HID 厂商自定义 | **Usage Page `0xFF00` / Usage `1`**：语音键与麦克风开关 |

语音键和键盘麦克风**只存在于 2.4G 接收器模式**。蓝牙 BLE 下键盘只有标准 HOGP，
既没有 `0xFF00` 通道也没有音频端点（见 `ble-notes.md`）。

## 2. 输入报告（接收器 → 主机）

`MI_05` 的输入报告 17 字节：`01` 是 Report ID，第 2 字节是命令。

| 报告 | 含义 |
| --- | --- |
| `01 B0 01 ...` | 语音键**按下** |
| `01 B0 03 ...` | 按住时的**重复帧**，约 400 ms 一次 |
| `01 B0 00 ...` | 语音键**松开** |
| `01 E1 <固件版本字符串>` | 查固件应答 |
| `01 D1 <设备标识>` | 查设备身份应答 |
| `01 E2 xx ...` | 状态 / 保活应答 |
| `01 B1 00 ...` | 语音通道初始化应答 |
| `01 B2 01/00 ...` | 麦克风开 / 关应答 |
| `01 00 00 68 ...` | 麦克风开始向 USB Audio 推流的边界 |
| `01 00 00 69 ...` | 麦克风停止推流的边界 |
| `01 E3 xx ...` | **链路事件**：键盘断开 / 重连时各一条（实测每个断电重开循环恰好一条，值 `0x05`） |

最后 1 字节是校验值。读取时不需要校验，可以直接忽略。

## 3. 输出报告（主机 → 接收器）

128 字节，`buffer[0] = 0x02`（Report ID），命令在 `buffer[1..2]`，`buffer[127]` 是固定校验值。
校验值是抓包得到的常量，**只需要写入，不需要反推算法**。

```text
E1 00 F3   查固件
D1 00 93   查设备身份
E2 00 F5   保活 / 状态
B1 00 53   初始化语音通道      ← 缺这一步麦克风永远不会通电
B2 01 3D   开启无线麦克风
B2 00 55   关闭无线麦克风
```

初始化是 `E1/D1/E2/B1` **两轮**，轮内间隔约 20 ms，轮间约 0.5 s（时序取自搜狗助手抓包）。
之后每 6 秒发一次 `E2` 保活。

## 4. 踩过的坑

### 4.1 必须用 `WriteFile`，`HidD_SetOutputReport` 会静默失效

原实现用 `HidD_SetOutputReport`，**返回值是 TRUE，但设备一条报告都收不到**
（它走 `IOCTL_HID_SET_OUTPUT_REPORT`）。表现是初始化握手和 `B2` 开关全部“成功”但毫无效果。

改用 `WriteFile`（`IOCTL_HID_WRITE_REPORT`）后设备应答立刻正常。判断依据：看有没有
`01 E1` / `01 D1` / `01 B1` 这些应答，没有就说明写入根本没到。

### 4.2 `ReadFile` 一次可能返回多条报告

HID 驱动一次可以返回多条报告拼在一起（实测三条 / 51 字节）。如果只检查 `buffer[0]`，
夹在中间的语音键报告会被丢弃。

做法：按 `HidP_GetCaps` 的 `InputReportByteLength`（本设备 17）分配缓冲区，保证一次一条。

### 4.3 每次开麦都有约 400 ms 的直流爆音

`B2 01` 之后设备会吐一段冲击：采样值 `0 → -15 → -46 → -114 → … → -27542 → -32768`，
然后卡在 int16 下限约 100 个样本，整体恢复要 300~400 ms。两次独立录音逐样本几乎一致，
说明是**设备自己产生的**，不是声学信号，也和音量设置无关。

做法：发完 `B2 01` 等 450 ms 再开始录音 / 触发听写。

### 4.4 键盘休眠后接收器输出全零 PCM

键盘闲置一会儿后无线链路会睡，此时音频端点仍能打开、录音文件仍然生成，但**样本全是 0**。
按一下键盘就能唤醒。

做法：录音后统计非零字节占比，几乎全零就提示用户先按一下键盘。

### 4.5 空闲时接收器不主动发任何东西

**这是最容易误判的一条。** 一开始用「连续 N 秒没收到报告 = 链路失效」做判活，
结果空闲时每 20 秒误报一次 —— 因为空闲时设备本来就一条报告都不发。

结论：**不能用静默超时判断链路是否存活**。空闲和链路死掉在报告层面无法区分。

### 4.6 `E2` 只在对它发 `E2` 之后才应答

主动发 `E2 00 F5`，实测 6/6 次都有 `01 E2` 应答，延迟约 375 ms。所以它是**可用的探针**，
但设备不会自己周期性上报。

### 4.7 按住语音键时断电，会让状态机永久卡住

按住期间把键盘关掉，「松开」报告永远不会到。如果代码用 `buttonHeld` 标志过滤重复帧，
标志就会永久停在“按住”，之后每次真实按键都被吞掉 —— 表现就是**“键盘关了再开就找不到键盘”**，
拔插接收器重建读循环才能恢复。

三层兜底（`MIIWVoiceWin.cs` 已实现）：

1. 收到 `01 E3` 链路事件时复位状态机（实测收到后 1 秒内即可继续正常识别）；
2. 区分 `B0 01`（新按下）与 `B0 03`（重复帧）：卡住时再来一个 `B0 01` 会自动收尾重来；
3. 空闲时每 60 秒静默重发一次初始化握手作为安全网。

另外实测：**键盘断电重开后语音通道本身会自愈**，不需要重连或重发握手，
真正会出问题的只有上面的状态机。

### 4.8 Windows 的麦克风音量滑块对这个设备无效

`IAudioEndpointVolume` 读到该端点的 dB 范围是 `0 .. +30`，但把它设成 0% 和 100%，
录出来的波形**逐样本一致**。所以没法靠系统音量调增益，只能依赖识别端。

### 4.9 `CloseHandle` 会等未完成的同步 I/O

读循环阻塞在 `ReadFile` 上时，直接 `CloseHandle` 会一直等到那个 I/O 被取消为止
（实测能把退出拖住好几秒）。必须**先 `CancelIoEx` 再关闭**。

## 5. 识别接口的时长边界

用合成音频实测 `mimo-v2.5-asr`（`chat/completions` + 单个 `input_audio` part）：

| 音频长度 | 返回字数 | 句数 | 是否完整 |
| --- | --- | --- | --- |
| 30 秒 | 120 | 6/6 | 完整 |
| **60 秒** | **240** | **12/12** | **完整** |
| 120 秒 | 20 | 1/12 | 只剩第一句 |
| 300 秒 | 20 | 1/12 | 只剩第一句 |

超长时**不报错、不提示**，直接静默截断，加 `max_tokens` 也无效。
所以录音上限设在 60 秒，不要调大。

## 6. 验证方法

协议这类东西靠读代码猜不出来，建议用**交互式脚本**验证：屏幕上一步步提示、按回车推进、
全程写日志，这样操作者能控制节奏，事后也能对着时间戳复盘。

值得定期回归的清单：

1. 初始化握手是否拿到 `E1/D1/B1` 应答（判断写入是否真的生效）
2. 按一次语音键，是否收到 `B0 01 → B0 03… → B0 00`
3. 按住语音键说一句话，录音是否非全零、识别结果是否正确
4. 按住语音键期间关掉键盘，重开后是否仍能正常识别（状态机回归）
5. 键盘断电重开后，日志里是否出现 `01 E3`
6. 点退出，托盘图标是否立即消失、进程是否在 1 秒内结束
